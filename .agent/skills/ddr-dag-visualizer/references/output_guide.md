# DDR DAG Visualizer — Output Interpretation Guide

This guide explains how to read and interpret the five output files
generated by the `ddr-dag-visualizer` skill.

---

## Input File Types

The skill accepts two types of DDR YAML definition files. Both produce
identical output artifacts.

| Type                  | Contents                                                                                                                                                                                                                                           | Example                       |
| --------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ----------------------------- |
| **System-definition** | Full DDR specification: `tier_definitions`, `axioms`, `operations`, `extension_catalog`, `nodes`, and all normative sections. Tier metadata is loaded dynamically — cluster labels include `layer_label`, `core_question`, and structural markers. | `ddr_system_v4.0.yaml`        |
| **Project-instance**  | Minimal: `ddr_version`, `active_tiers`, `nodes`. Tier metadata falls back to hardcoded DDR v4.0 defaults.                                                                                                                                          | Any project-specific DDR file |

## ddr_dag_full.svg / .png

The primary design artifact. A complete rendering of the DDR DAG.

### Tier Clusters (Colored Bands)

Each horizontal band is one active DDR tier. When a system-definition file
is used, each cluster label shows (top to bottom): **layer designation**,
**tier ID with structural markers**, **full tier name**, and the
**first line of the tier's core question**.

| Tier   | Band Color              | Structural Marker          |
| ------ | ----------------------- | -------------------------- |
| XPD    | Green (dashed border)   | `[OPTIONAL]`               |
| SIL    | Deep blue               | — (root when XPD inactive) |
| GPCL   | Deep blue               | —                          |
| FCL    | Deep blue               | —                          |
| CL     | Amber (dashed border)   | `[OPTIONAL]`               |
| SAL    | Deep red (thick border) | `← MERGE NODE`             |
| ICL    | Deep blue               | —                          |
| CDL    | Deep blue               | —                          |
| ISL    | Deep blue               | `← TERMINAL LEAF`          |

### Node Colors (Status Encoding)

| Fill Color            | Status     | Meaning                              |
| --------------------- | ---------- | ------------------------------------ |
| Tier color (solid)    | ACTIVE     | Validated, production-ready          |
| Gray                  | DRAFT      | Proposed, not yet validated          |
| Orange (thick border) | DIRTY      | Requires re-validation post-mutation |
| Light gray (faded)    | DEPRECATED | Scheduled for replacement            |
| Dark gray             | SUPERSEDED | Replaced; retained for audit trail   |

### Edge Styles (Relationship Encoding)

| Style        | Color   | Relationship                              |
| ------------ | ------- | ----------------------------------------- |
| Solid arrow  | Black   | `derives` — child derived from parent     |
| Dashed arrow | Amber   | `constrains` — parent bounds child design |
| Solid arrow  | Green   | `implements` — child realizes parent spec |
| Dotted arrow | Purple  | `extends` — Extension annotates Core node |

### Reading the SAL Merge Node

SAL (System Architecture Layer) is the only tier that legitimately
receives two parent edges simultaneously: FCL (`derives`) and CL
(`constrains`, when CL is active). Two incoming edges to a SAL node —
one solid black and one dashed amber — is the correct and expected
pattern. The thick red cluster border marks the merge node visually.

## ddr_dag_tiers.svg

The tier topology overview. When generated from a system-definition file,
the topology edges and optional/merge/terminal tier markers are derived
directly from `tier_definitions` rather than hardcoded. Inactive optional
tiers are rendered in gray with dashed borders; inactive edges are gray.

Use this diagram for:

- High-level architectural review
- Specification documentation headers
- Confirming optional tier activation state (XPD, CL)
- Verifying the SAL merge-node pattern

## validation_report.md

The human-readable VERIFY output. Sections:

1. **Header table** — project name, DDR version, CLEAN/DIRTY status,
   node count, violation count.
2. **Node Statistics** — counts per tier and per status.
3. **Violations** — each violation listed with:
   - Severity: ⛔ CRITICAL, 🔴 ERROR, 🟡 WARNING
   - Rule ID referencing DDR v4.0 §2–§7
   - Affected node or edge ID
   - Description with architectural consequence

Rule `INV-MANDATORY` (ERROR) fires when a mandatory tier is absent from
`active_tiers`. This check is only possible when `tier_definitions` is
present; it falls back to the 7 spec-defined mandatory tiers otherwise.

A project is CLEAN only when violations is empty AND no nodes carry
`DIRTY` status.

## validation_report.json

The machine-readable VERIFY output. Intended for direct LLM ingestion
alongside the SVG visualizations for multimodal structural quality
assessment. Structure:

```json
{
  "project":         "string",
  "ddr_version":     "4.0",
  "clean":           true,
  "node_count":      9,
  "tier_counts":     { "SIL": 1, "GPCL": 1, ... },
  "status_counts":   { "ACTIVE": 9 },
  "violation_count": 0,
  "violations": [
    {
      "rule_id":     "AX-7",
      "node_id":     "SAL-5.1 -> GPCL-2.1",
      "description": "...",
      "severity":    "CRITICAL"
    }
  ]
}
```
