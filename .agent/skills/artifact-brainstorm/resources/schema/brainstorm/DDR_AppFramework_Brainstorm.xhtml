PART  I

Document Manifest — Self-Description, Usage, and Schema

 

 

Part I is permanent and immutable. It defines how this document works: its structure, the entry schema, the classification taxonomy, conventions for adding new sections, and the governance model for promoting ideas to formal design status. Read Part I before contributing any entry.

§1  Document Purpose and Scope

This Brainstorming Compendium serves as the singular, structured repository for nascent ideas, architectural directions, library candidates, and design hypotheses related to the construction of a standalone application framework built on top of the DDR System v6.3 specification. It is intentionally broader and less constrained than a formal specification — its value is in capturing ideas at the earliest possible stage, before premature decisions eliminate valid paths.

 

1.1  What Belongs Here

  • •Application architecture and design patterns being considered for the DDR App Framework. 

  • •Open-source library candidates (any language; commercially licensable) with relevance to DDR concerns. 

  • •Integration hypotheses between the DDR Extension System (E1–E9) and application-layer tooling. 

  • •User experience and workflow concepts for DDR node CRUD, graph visualization, and project management. 

  • •Data persistence, serialization, and interchange format ideas. 

  • •Deferred or parked ideas that are not immediately actionable but worth retaining. 

 

1.2  What Does Not Belong Here

  • •Finalized engineering decisions — these belong in ADRs or the formal DDR specification. 

  • •Implementation code — no production code is authored inside this document. 

  • •Bug reports or operational issue tracking — use the DDR Issue Tracker. 

  • •Content duplicating the normative DDR System v6.3 specification — reference it, do not replicate it.

§4  Rules for Adding New Sections

Follow these rules strictly when appending new content to this document. Structural consistency is what makes the document searchable and maintainable at scale.

 

4.1  Adding a New Entry to an Existing Section

  1. 1.Assign the next sequential entry_id within the current Part (e.g., BRAIN-II-004). 

  2. 2.Populate all Common Fields (§3.1). Leave no Common Field blank — use TBD for genuinely unknown values. 

  3. 3.Select the entry type-specific fields from §3.2 or §3.3 as appropriate. 

  4. 4.Enter the entry using the visual entry block format established in Part II and Part III. 

  5. 5.Update the Section Index table at the top of the owning Part if one exists. 

  6. 6.Do not renumber or remove existing entry IDs. Entries are append-only; use SUPERSEDED status to retire. 

 

4.2  Adding a New Subsection Within a Part

  1. 7.New subsections are numbered sequentially within their Part (e.g., §II.4, §II.5...). 

  2. 8.Subsection titles must correspond to a Category ID in the taxonomy (§3.4) unless the subsection is structural (e.g., Index, Summary). 

  3. 9.Each new subsection should open with a 1–2 sentence scope statement before the first entry block. 

 

4.3  Adding a New Part

  1. 10.Verify that no existing Part or reserved slot already covers the intended category space. 

  2. 11.Register the new Part in the Part Registry (§2.1) with status ACTIVE before writing any content. 

  3. 12.Open the new Part with a cover block identical in structure to the covers used in Part II and Part III. 

  4. 13.Define a Section Index table as the first content element of the new Part. 

  5. 14.Assign entry IDs starting at BRAIN-{PART#}-001. 

§5  Governance and Promotion Protocol

This section defines how ideas move from brainstorm entries into formal design artifacts. The document itself never becomes authoritative — it is always a feeder for the DDR formal specification and Architecture Decision Records.

 

5.1  Promotion Criteria

An entry may be promoted to CANDIDATE status when all of the following are true:

  • •All Common Fields (§3.1) are fully populated — no TBD values remain except in open_questions. 

  • •The open_questions list contains only questions that are acceptable to carry into a design evaluation, not questions that block understanding of the idea. 

  • •At least one DDR tier or extension has been identified in ddr_relevance. 

  • •Commercial licensing viability has been assessed (LIB entries: commercial_use = YES). 

 

An entry may be promoted to PROMOTED status (and thus out of this document) when:

  • •A corresponding Architecture Decision Record (ADR) has been drafted and assigned a reference ID. 

  • •The relevant DDR tier owners or the Architecture Board have reviewed the entry. 

  • •The 'references' field contains the ADR ID and any relevant spec section that will be updated. 

 

5.2  Review Cadence

  • •Document review is recommended at the start of each new development cycle or sprint. 

  • •Entries in EXPLORING status for more than two consecutive cycles should be moved to PARKED or REJECTED. 

  • •HIGH priority entries without progress after one cycle should be downgraded to MED or reassigned. 

 

IMPORTANT — DDR Axiom Alignment

No promoted idea may introduce a dependency that violates DDR AX-3 (Determinism), AX-6 (Declarative Integrity), or AX-7 (DAG Acyclicity). Before promotion, each IDEA entry must include an explicit statement in ddr_constraints confirming these axioms are respected, or documenting the exemption rationale.

§II.1  Application Architecture Overview

This section captures early thinking about the structural decomposition of the DDR App Framework. Entries address questions of layering, module boundaries, deployment topology, and the application's relationship to the DDR specification files it manages.

 

[BRAIN-II-001] Three-Layer Application Architecture  ● HIGH  [CAT-ARCH]

Decompose the DDR App Framework into three distinct, cleanly-separated layers: Core Engine, Service Layer, and Presentation Layer.

Detail: The Core Engine wraps all DDR-specification logic: DAG construction, topological sorting, lifecycle state machine, schema validation, and extension orchestration. It exposes no UI and has no I/O side effects beyond the project file system. The Service Layer mediates between the Core Engine and any presentation surface (CLI, REST API, or desktop GUI) through a typed command/query interface that mirrors the DDR Operations Protocol (§7). The Presentation Layer is fully replaceable — first implementation may be a rich desktop GUI (PySide6 or Electron), later joined by a CLI and a REST endpoint. This separation ensures the engine can be validated in isolation and that the DDR specification logic never leaks into UI code.

Open Questions: Is the Service Layer a Python in-process module or a separate process/subprocess? How does the command interface map to DDR operations (INSERT, ACTIVATE, MODIFY, SUPERSEDE, DEPRECATE, VALIDATE, BUNDLE, UNBUNDLE)? Does the Core Engine need to be distributable as a standalone PyPI package?

 

[BRAIN-II-002] DDR Project as a File-System-First Store  ● HIGH  [CAT-STORE]

Treat a DDR project as a structured directory tree where each node is a YAML file, making the project natively VCS-friendly without requiring a database.

Detail: A DDR project root contains: a project manifest (ddr_project.yaml), an active_tiers declaration, a nodes/ directory tree partitioned by tier (nodes/XPD/, nodes/SIL/, etc.), and an .agent/ directory for extension state (matching the ARE checkpoint path in ARE-R7). Each node file is named {node_id}.yaml and conforms to ddr_node_schema_v6.3.yaml. This approach makes every structural change a diff-able file change, enables git blame on individual nodes, and eliminates a database dependency for single-user projects. A database backend (SQLite, PostgreSQL) would be an optional, swappable layer for performance at scale or multi-user collaboration.

Open Questions: How are cross-node graph edges stored — fully within parent_ids in each child file, or also as an adjacency index? What is the performance boundary at which the file-system store becomes untenable and a DB layer is required? How does the project manifest handle express_mode document profiles vs. full project_instance profiles?

 

[BRAIN-II-003] Unified Operations Protocol API Surface  ● HIGH  [CAT-ARCH]

Expose all DDR mutation operations through a single, strongly-typed API surface that directly mirrors the Operations Protocol (§7): INSERT, ACTIVATE, MODIFY, SUPERSEDE, DEPRECATE, VALIDATE, BUNDLE, UNBUNDLE_SCAN, UNBUNDLE_EXECUTE.

Detail: Every state-mutating action the application performs must flow through named Operation objects that carry pre-condition checks, atomic execution logic, and post-condition assertions — matching the DDR operation contract structure. Operations are logged to an append-only operation journal (.agent/journal/ops.log). This ensures that the application is always auditable, that the DDR lifecycle state machine cannot be bypassed via direct file edits, and that the operation vocabulary in the UI matches exactly the vocabulary in the spec. READ operations (VALIDATE reads, graph traversals) are separate and do not go through the journal.

Open Questions: Should the operation journal be YAML or NDJSON? How are failed operations (pre-condition violation) surfaced to the user? Is VALIDATE a pure query or does it produce annotated output that must be persisted?

 

[BRAIN-II-004] Plugin Architecture for DDR Extensions (E1–E9)  ● MED  [CAT-EXT]

Implement the DDR Extension System (§8) as a first-class plugin architecture: each extension (E1–E9) ships as a discrete, dynamically-loadable plugin with a declared contract, reads/annotates manifests, and activation state.

Detail: A PluginRegistry maintains loaded extension instances, their declared contracts (reads[], annotates[], activation state), and the extension's connection to the Candidate Pool (§8.2). Extensions are loaded from a plugins/ directory or installed via the package manager. The ARE extension (E5) plugin is special: it manages tri-state lifecycle per ARE-R6, maintains the checkpoint file per ARE-R7, and enforces the scoring_profile contract per ARE-R2/R5. Extension plugins must not mutate Core DAG nodes directly — they communicate exclusively through the read/annotate interfaces defined in the extension contract.

Open Questions: What is the plugin isolation model — subprocess, shared in-process namespace, or dynamic module import? How are extension contracts validated at load time? Should extension plugins be first-party only, or is the architecture open to third-party extensions?

§II.2  DAG Engine Design

The DAG Engine is the most critical internal component of the DDR App Framework. It owns all graph operations: construction from the file-system store, invariant enforcement, topological ordering, cycle detection, and DIRTY propagation.

 

[BRAIN-II-005] In-Memory DAG Representation with Lazy Hydration  ● HIGH  [CAT-DAG]

Maintain the active DDR project graph as a fully in-memory directed acyclic graph, hydrated lazily from the file-system store on access, with a dirty-tracking cache invalidation scheme.

Detail: On project open, only the project manifest and node index are loaded. Individual node YAML files are hydrated into memory on first access and cached. The cache records each node's file mtime to detect out-of-band edits. The in-memory representation uses an adjacency list keyed by node ID (not tier), supporting fast parent_ids lookups, ancestor traversal, and descendant fanout queries. Topological sort is recomputed lazily on demand and memoized until the graph is mutated. Cycle detection runs on every INSERT and MODIFY operation before the operation is committed (satisfying AX-7).

Open Questions: What Python graph library best fits this model? (networkx is the obvious candidate — see Part III.) How does lazy hydration interact with VALIDATE, which may need to traverse the full graph? At what graph size does the lazy strategy break down and a full pre-load become necessary?

 

[BRAIN-II-006] DIRTY Propagation Engine  ● MED  [CAT-DAG]

Implement the DDR DIRTY status propagation rule as an explicit graph traversal pass triggered by MODIFY, SUPERSEDE, and DEPRECATE operations, propagating downstream from the mutated node.

Detail: When a node transitions to DIRTY status (or when its ACTIVE status changes), all descendant nodes whose parent_ids reference the mutated node receive a DIRTY annotation. The propagation is a depth-first post-order traversal from the mutated node outward through all descendant edges. The propagation engine respects tier boundaries — a DIRTY annotation on an XPD node does not automatically cascade to ISL nodes without traversing all intermediate tiers. The operation journal records each propagation event. DIRTY propagation is synchronous and atomic with the triggering operation.

Open Questions: Should DIRTY propagation be immediate and blocking, or deferred and queued? How does the UI communicate a DIRTY cascade to the user — annotation badges, a propagation report? Does DIRTY propagation apply to Extension Candidate Pool entries, or only Core DAG nodes?

§II.3  Node CRUD and Editing Surface

This section addresses how users create, read, update, and delete DDR nodes, with a focus on making the DDR operation semantics visible and enforceable in the editing UI.

 

[BRAIN-II-007] Tier-Aware Node Editor with Inline Atomic Rule Guidance  ● HIGH  [CAT-CRUD]

Provide a structured node editor that is aware of the active tier context and surfaces the relevant atomic ruleset (from the Tier Definitions §5) as inline guidance during authoring.

Detail: When a user is editing an FCL node, the editor displays the FCL atomic rules (FCL-R1 through FCL-R7 etc.) as collapsible guidance alongside the content field. The editor provides real-time feedback (via the VALIDATE operation) on whether the current content draft satisfies the tier's atomic rules. The parent_ids field renders as a searchable node picker that constrains selectable parents to the legal edge_type/tier combinations for the current node's tier (per the DAG invariants §3.5). The status field renders as a lifecycle transition widget showing only the valid next states from the current status (per the lifecycle.status_transitions authority block §3.8).

Open Questions: How are constraint_origin (CL-only) and prior_status (SUPERSEDE_PENDING) fields handled in the editor? Should the editor support side-by-side diff view for SUPERSEDE workflows? Is a form-based editor sufficient, or is a structured Markdown editor with YAML front-matter a better authoring experience?

 

[BRAIN-II-008] Express Mode Project Scaffolding Wizard  ● MED  [CAT-CRUD]

Provide a project scaffolding wizard specifically for Express Mode (§4 Consumption Modes) that generates the canonical group compositions and the UNBUNDLE_SCAN / UNBUNDLE_EXECUTE authority block in a guided, step-by-step workflow.

Detail: Express Mode projects have fixed group compositions and require the full express_mode authority block. A scaffolding wizard collects project name, active tiers, and express group assignments from the user in a guided flow, then generates the complete project directory structure and a skeleton ddr_project.yaml conforming to the project_instance_express document profile. The wizard validates group compositions against the fixed structural rules before generating output, preventing the silent re-definition issue that v6.3 was designed to close.

Open Questions: Should the wizard also scaffold representative nodes for each active tier? Is the wizard a CLI command (ddr init --express), a GUI dialog, or both? How does the wizard handle the case where the user wants a full project_instance profile rather than express?

§II.4  Validation and Schema Enforcement

Validation is the DDR system's primary quality gate. This section explores how the VALIDATE operation is surfaced to the user and how schema conformance is continuously maintained.

 

[BRAIN-II-009] Continuous Background Validation with Severity-Classified Findings  ● HIGH  [CAT-VALID]

Run the VALIDATE operation as a continuous background process triggered by any file-system change to the project, surfacing findings classified by severity (BLOCKER, ERROR, WARNING, INFO) in a persistent findings panel.

Detail: The Validation Engine subscribes to file-system events on the project's nodes/ directory. On any change, it schedules a debounced re-validation pass for the affected nodes and their descendants. Findings are classified using the compliance checklist (§11) severity tiers: BLOCKER (schema violation, cycle detected, axiom violation), ERROR (atomic rule failure, lifecycle violation), WARNING (tier abstraction boundary breach, missing recommended fields), INFO (advisory from extensions). The findings panel persists between sessions and links each finding to the specific node ID and rule ID that generated it. BUNDLE and UNBUNDLE_EXECUTE operations are gated on a BLOCKER-free validation state.

Open Questions: How are validation findings from Extension System annotators (E1–E9) distinguished from Core validation findings? Should background validation be opt-in or always-on? What is the performance budget for re-validation on large projects (1000+ nodes)?

§II.5  Extension System Integration

The DDR Extension System (§8, §9) defines nine named extensions (E1–E9) with reads/annotates contracts. This section explores how those extensions are integrated into the application layer.

 

[BRAIN-II-010] ARE Candidate Pool Review Interface  ● MED  [CAT-EXT]

Build a dedicated UI panel for managing the ARE Extension (E5) Candidate Pool, supporting review, scoring visualization, and one-click promotion via INSERT.

Detail: The ARE Candidate Pool panel displays all candidates in the Pool, sorted by confidence_score descending. Each candidate shows its ARE::confidence_score, the active score_band label (speculative / probable / high_confidence), the review_status, and practitioner notes. The panel renders the scored candidate's evidence — the source tiers that contributed to the inference. A promote button triggers the INSERT operation on the candidate, with full atomic ruleset validation. The panel also surfaces the ARE activation state (active/paused/disabled) and the ARE-R6 transition controls. The checkpoint file path (ARE-R7) is shown as a status indicator.

Open Questions: Should the Candidate Pool panel support bulk review or only single-candidate actions? How is the scoring_profile (standard_v1 / conservative_v1 / custom) visualized in the panel? Should the panel support override_flag + human_rationale for below-threshold candidates?

§II.6  AI and Agentic Interface

The DDR App Framework is designed to be used with and by AI agents. This section explores how the application exposes itself to agentic coding assistants and LLM-based tooling.

 

[BRAIN-II-011] AGENTS.md Auto-Generation from Active Project  ● MED  [CAT-AI]

Provide a command that auto-generates an AGENTS.md file from the live DDR project state, scoped to the active tiers and current node population — optimized for agentic coding contexts (Codex, Claude Code).

Detail: The generated AGENTS.md would include: the active tier list and their atomic rule summaries, a listing of all ACTIVE nodes by tier with IDs and titles, the current operation contract surface, all BLOCKER and ERROR validation findings, and a concise project context block describing the project intent derived from the XPD nodes. The generation is parameterized by verbosity level (Express / Standard / Full) to control context window size when targeting specific agents. This directly supports the agentic coding workflow that has been established through prior DDR System development iterations.

Open Questions: Should AGENTS.md generation be a built-in command (ddr export agents-md) or a named extension? How are Express Mode projects handled differently from full project_instance profiles in the output? Should the output format be configurable (Markdown, YAML front-matter + Markdown, JSON)?

 

[BRAIN-II-012] MCP Server Exposure for DDR Project Operations  ● LOW  [CAT-AI]

Expose the DDR App Framework's Operation API as an MCP (Model Context Protocol) server, allowing AI coding assistants with MCP client support to directly issue DDR operations against a live project.

Detail: An optional --mcp-server launch mode would start the DDR App Framework as an MCP server, advertising the DDR Operation tools: INSERT, ACTIVATE, MODIFY, SUPERSEDE, DEPRECATE, VALIDATE, BUNDLE, UNBUNDLE_SCAN, UNBUNDLE_EXECUTE. Each tool's schema would be derived directly from the Operations Protocol definitions (§7). An AI agent with MCP client support could then directly author, validate, and lifecycle-manage DDR nodes without intermediary file manipulation — giving the agent a semantically-rich, operations-level interface rather than raw YAML editing.

Open Questions: Which MCP server SDK (Python mcp-server, TypeScript MCP SDK) is the right choice? How are authentication and project-scope isolation handled in the MCP server mode? Is this valuable enough vs. simply having agents edit YAML files directly per the existing AGENTS.md workflow?

Mature, comprehensive Python graph library supporting directed graphs (DiGraph, DAG), topological sort, cycle detection (is_directed_acyclic_graph), shortest path, reachability, and graph I/O (GraphML, GEXF, JSON). De-facto standard for Python graph computation.

Relevance: Directly addresses CAT-DAG requirements: DiGraph maps naturally to the DDR node/edge model. Topological sort satisfies the tier ordering invariant. is_directed_acyclic_graph() is the cycle detection primitive for AX-7 enforcement. Ancestor/descendant queries support DIRTY propagation traversal (BRAIN-II-006). node and edge attribute dicts hold DDR metadata. Serialization to JSON (node-link format) is available.

DDR Tiers Touched: All DDR tiers (XPD through ISL); Core DAG Engine (BRAIN-II-005)

Notes: Large dependency but extremely battle-tested. Pure Python — no native extensions required. Performance is adequate for projects up to ~10k nodes; beyond that, consider graph-tool or igraph bindings. Verdict: CANDIDATE.

 

[BRAIN-III-002] graphlib (stdlib)  —  PSF License (effectively BSD)

Python 3.9+ standard library — graphlib  |  No install required

Python standard library module (3.9+) providing TopologicalSorter — a lean, dependency-free topological sorter for DAGs. Minimal API: prepare(), get_ready(), done(). Raises CycleError on cycles.

Relevance: Zero-dependency topological sort for the DDR tier ordering and operation sequencing. Cannot replace NetworkX for full graph analytics, but is a clean, auditable primitive for the topological sort sub-problem within the DAG Engine. Consider using graphlib for the sort and NetworkX for structural analysis — avoids pulling NetworkX as a hard dependency if only sort + cycle detection are needed in the Core Engine.

DDR Tiers Touched: Core DAG Engine — tier ordering and pre-condition sequencing

Notes: Stdlib inclusion removes a PyPI dependency for the most critical path. Does not support edge attributes or traversal queries — NetworkX still needed for full DDR graph representation. Verdict: CANDIDATE for sort primitive; BRAIN-III-001 for full graph model.

 

[BRAIN-III-003] rustworkx  —  Apache-2.0

https://github.com/Qiskit/rustworkx  |  pip: rustworkx

High-performance graph library with a Python API backed by a Rust implementation. Significantly faster than NetworkX for large graphs. Supports DiGraph, DAG detection (is_directed_acyclic_graph), topological sort, and node/edge attribute payloads.

Relevance: Performance-tier alternative to NetworkX for projects where graph size or validation latency becomes a concern (BRAIN-II-009 background validation budget). Drop-in replacement for most NetworkX DAG operations. API is similar but not identical to NetworkX — migration cost is modest. Apache-2.0 license is commercially clean.

DDR Tiers Touched: Core DAG Engine — performance-critical traversal and validation paths

Notes: Requires Rust toolchain for builds from source; pre-built wheels available for common platforms. Consider as a PHASE-2 optimization swap when NetworkX becomes a bottleneck. Verdict: EXPLORING — hold for performance benchmarking phase.

§III.2  Graph Visualization Libraries

Libraries for rendering DDR project graphs as navigable, tier-aware visual diagrams.

 

[BRAIN-III-004] Cytoscape.js  —  MIT

https://github.com/cytoscape/cytoscape.js  |  npm: cytoscape

Battle-tested JavaScript graph visualization library. Supports directed graphs with custom node/edge styling, multiple layout algorithms (dagre, elk, cola, concentric), interactive pan/zoom, and event-driven interaction. Runs in browser or Node.js (headless).

Relevance: Primary candidate for the DDR tier-map visualization panel if the Presentation Layer uses a web-based renderer (Electron, Tauri, or a built-in browser widget). Tier-color-coded nodes, edge-type-distinguished arrows (derives/constrains/implements), and status-badge overlays are all achievable with Cytoscape.js custom styling. The dagre layout plugin produces a top-down DAG layout naturally aligned with DDR tier ordering.

DDR Tiers Touched: All DDR tiers (visual representation); CAT-VIZ

Notes: MIT license is commercially clean. Requires a JavaScript/WebView surface — does not run natively in a Python Qt widget without a WebEngineView or similar. Layout plugins (dagre, elk) are separate packages. Verdict: CANDIDATE for web-based Presentation Layer. Evaluate against Graphviz/PyGraphviz for static export.

 

[BRAIN-III-005] Graphviz + PyGraphviz / graphviz (Python)  —  MIT (Python binding); CPL-1.0 (Graphviz engine, compatible with commercial use)

https://github.com/xflr6/graphviz  |  pip: graphviz

Python interface to the Graphviz DOT language renderer. Supports directed graphs (Digraph), automatic hierarchical layout (dot engine — ideal for DAGs), and SVG/PNG/PDF export. Two Python wrappers: 'graphviz' (pure DOT generator, recommended) and 'PyGraphviz' (NetworkX integration).

Relevance: Ideal for static export of DDR project tier maps: SVG/PNG reports, documentation attachments, and BUNDLE outputs that include a visual graph snapshot. The 'dot' layout engine's top-down hierarchy maps directly to DDR's 9-tier topology. NetworkX has a built-in nx.drawing.nx_agraph.to_agraph() bridge for PyGraphviz integration, allowing the in-memory NetworkX graph (BRAIN-III-001) to be rendered without a secondary model.

DDR Tiers Touched: All tiers — static export; BUNDLE output (§7 Operations)

Notes: Requires Graphviz system binary (apt/brew/winget install graphviz). Not suitable for interactive visualization — use Cytoscape.js (BRAIN-III-004) for that. Verdict: CANDIDATE for static report export.

 

[BRAIN-III-006] Mermaid.js  —  MIT

https://github.com/mermaid-js/mermaid  |  npm: mermaid

Diagram-as-code JavaScript library rendering Markdown-like diagram syntax into SVG in a browser. Supports flowcharts, sequence diagrams, gitgraph, and class diagrams. Can be rendered server-side via mermaid-js/mermaid CLI (Node).

Relevance: Alternative lightweight visualization path — the DDR App Framework could export a DDR project graph as a Mermaid flowchart string (generated from the NetworkX model), which could then be rendered client-side in any web surface or embedded in Markdown documentation. Particularly relevant for AGENTS.md integration (BRAIN-II-011) — a Mermaid diagram of the active project DAG would be a compact, text-based visual context block for AI agents.

DDR Tiers Touched: All tiers — documentation export; AGENTS.md integration (BRAIN-II-011)

Notes: Mermaid diagrams have a complexity ceiling — very large graphs become unreadable. Best suited for per-tier subgraph views rather than full project renders. Verdict: CANDIDATE for documentation export and AGENTS.md visual context.

§III.3  YAML / JSON Schema Validation

Libraries for enforcing DDR node schema conformance (ddr_node_schema_v6.3.yaml) and structural invariant checking.

 

[BRAIN-III-007] jsonschema  —  MIT

https://github.com/python-jsonschema/jsonschema  |  pip: jsonschema

Reference Python implementation of JSON Schema validation supporting drafts 4 through 2020-12. Provides Draft202012Validator, custom error formatting, and format checkers.

Relevance: The ddr_node_schema_v6.3.yaml conforms to JSON Schema 2020-12 (as stated in the file header). jsonschema's Draft202012Validator is the direct implementation match. Validation errors include path context (allowing the UI to pinpoint the failing field). Custom format checkers can enforce DDR-specific patterns (e.g., node ID format TIER-N.M, rule ID families). Consider pairing with PyYAML or ruamel.yaml for YAML-to-dict parsing before validation.

DDR Tiers Touched: All tiers — schema conformance; VALIDATE operation (§7)

Notes: May be slow for bulk validation of large node sets — consider caching compiled validators. Verdict: CANDIDATE. Primary schema validation library.

 

[BRAIN-III-008] Pydantic v2  —  MIT

https://github.com/pydantic/pydantic  |  pip: pydantic

Data validation and settings management library for Python using type annotations. v2 is Rust-backed for high performance. Supports JSON Schema generation from Python models, strict type coercion, and custom validators.

Relevance: Pydantic v2 models can represent the DDR node schema as Python dataclasses with full type safety. The Core Engine's in-memory node representation would benefit from Pydantic models: automatic validation on construction, IDE type inference, and JSON Schema generation (allowing the Pydantic model to serve as the schema authority). Pydantic and jsonschema (BRAIN-III-007) are complementary: jsonschema for YAML file validation at the boundary; Pydantic for in-memory type safety within the Core Engine.

DDR Tiers Touched: Core Engine in-memory model; all tiers

Notes: Rust-backed v2 is significantly faster than v1. The dual-validation approach (jsonschema at the file boundary + Pydantic in memory) adds complexity — evaluate whether Pydantic alone is sufficient. Verdict: CANDIDATE.

 

[BRAIN-III-009] ruamel.yaml  —  MIT

https://sourceforge.net/projects/ruamel-yaml/  |  pip: ruamel.yaml

YAML 1.2 compliant parser/emitter for Python. Preserves comments, formatting, and key order on round-trip reads/writes — unlike PyYAML which strips comments. Supports YAML anchors, merge keys, and custom constructors.

Relevance: Critical for the file-system-first store (BRAIN-II-002): DDR node YAML files may contain author comments that should be preserved across edit cycles. ruamel.yaml's round-trip mode reads and writes YAML without stripping user comments, preserving the human-authored annotation layer. The ddr_node_schema_v6.3.yaml itself is a comment-rich document — ruamel.yaml is the correct parser for loading it without data loss.

DDR Tiers Touched: File-system store (BRAIN-II-002); schema loading; node YAML I/O

Notes: PyYAML is simpler and faster but loses comments on write. ruamel.yaml is the correct choice for a tool that manages user-authored YAML files. Verdict: CANDIDATE. Replace PyYAML as the YAML I/O layer.

§III.4  Desktop GUI Frameworks

Frameworks for the Presentation Layer of the DDR App Framework targeting desktop deployment.

 

[BRAIN-III-010] PySide6 (Qt for Python)  —  LGPL-3.0 (dynamic link) / Commercial Qt License

https://doc.qt.io/qtforpython/  |  pip: PySide6

Official Qt binding for Python. Provides the full Qt widget toolkit, QML for declarative UIs, WebEngineView (Chromium-based web renderer for Cytoscape.js integration), file-system watchers (QFileSystemWatcher), threads, and signal/slot architecture.

Relevance: Established choice based on prior DDR-adjacent work (Local Dev Toolbox v7.3). QWebEngineView enables embedding Cytoscape.js (BRAIN-III-004) for the graph visualization panel without a separate Electron dependency. QFileSystemWatcher drives the background validation trigger (BRAIN-II-009). Qt's signal/slot model maps naturally to the DAG Engine event model.

DDR Tiers Touched: Presentation Layer (all tiers via UI); CAT-UX; CAT-VIZ integration

Notes: LGPL-3.0 requires dynamic linking for commercial distribution — do not statically link Qt. Qt Commercial license is an option for closed-source projects that cannot comply with LGPL. PySide6 is the officially supported binding (vs. PyQt6 which is GPL/commercial). Verdict: CANDIDATE (pending LGPL dynamic-link compliance confirmation).

 

[BRAIN-III-011] Tauri (Rust + WebView)  —  MIT / Apache-2.0 (dual)

https://github.com/tauri-apps/tauri  |  cargo: tauri

Lightweight cross-platform desktop application framework using the system's native WebView and a Rust backend. Much smaller binary footprint than Electron. JavaScript/TypeScript frontend; Rust backend with Python interop via sidecar subprocess.

Relevance: Alternative to Electron for a web-frontend-based Presentation Layer. If the DDR App UI is built in React/Vue with Cytoscape.js, Tauri is a compelling distribution target: smaller than Electron, dual MIT/Apache license, and no Chromium bundling. The Python Core Engine would run as a sidecar subprocess communicating over stdin/stdout or a local socket — preserving the Python-first Core Engine while using a web frontend. This maps directly to the three-layer architecture (BRAIN-II-001).

DDR Tiers Touched: Presentation Layer; distribution and packaging (CAT-DIST)

Notes: Requires Rust toolchain for builds. Python interop is sidecar-based — adds IPC complexity. WebView behavior varies by OS (Edge on Windows, WebKit on macOS, WebKitGTK on Linux). Verdict: EXPLORING — evaluate vs. PySide6+WebEngineView as the primary Presentation Layer.

§III.5  File-System Watching and Event Handling

Libraries for monitoring DDR project directory changes to trigger background validation.

 

[BRAIN-III-012] watchdog  —  Apache-2.0

https://github.com/gorakhargosh/watchdog  |  pip: watchdog

Cross-platform Python library for monitoring file-system events. Provides Observer/Handler pattern with events for file creation, modification, deletion, and movement. Uses native OS APIs (inotify, kqueue, FSEvents, ReadDirectoryChanges).

Relevance: Drives the background validation trigger in BRAIN-II-009 outside of a Qt environment. If the Core Engine runs headlessly (e.g., as a service process separate from the GUI), watchdog is the correct file-system watch primitive. In PySide6 context, QFileSystemWatcher (built into Qt) is the alternative — watchdog is the correct choice for a headless or CLI deployment mode.

DDR Tiers Touched: Core Engine — background validation (BRAIN-II-009); file-system store (BRAIN-II-002)

Notes: Apache-2.0 is commercially clean. Verdict: CANDIDATE for headless/CLI deployment; QFileSystemWatcher for PySide6 Presentation Layer.

§III.6  Serialization and Data Modeling

Libraries for data interchange, serialization, and project archive formats.

 

[BRAIN-III-013] msgspec  —  BSD-3-Clause

https://github.com/jcrist/msgspec  |  pip: msgspec

High-performance Python library for serialization and validation using native Python type hints. Supports JSON, MessagePack, and YAML decoding/encoding. Significantly faster than Pydantic v1 and competitive with Pydantic v2 for validation-heavy workloads.

Relevance: Alternative to Pydantic (BRAIN-III-008) for the Core Engine's in-memory node representation if raw serialization throughput is a concern. msgspec Struct types are particularly efficient for bulk VALIDATE passes over large node populations. The YAML support (via the upcoming msgspec.yaml module) could unify the YAML I/O and validation concern into a single library — pending maturity assessment.

DDR Tiers Touched: Core Engine — bulk validation performance; large project support

Notes: Less ecosystem momentum than Pydantic. YAML support is newer and less mature. BSD-3-Clause is commercially clean. Verdict: EXPLORING — benchmark against Pydantic v2 for large-project validation throughput.

 

[BRAIN-III-014] zipfile / tarfile (stdlib) + zipimport  —  PSF License

Python standard library — No install required

Python standard library modules for creating and reading ZIP and TAR archives. Directly support the DDR BUNDLE and UNBUNDLE operations which produce a project archive.

Relevance: The BUNDLE operation (§7 Operations Protocol) produces a distributable project archive. Python's stdlib zipfile module is a zero-dependency implementation path for creating DDR project bundles (.ddr.zip or .ddr.tar.gz). The archive format can be self-describing by including a bundle_manifest.yaml at the root, derived from the project manifest and the current VALIDATE findings report.

DDR Tiers Touched: BUNDLE / UNBUNDLE_SCAN / UNBUNDLE_EXECUTE operations (§7)

Notes: No external dependency needed for the bundle format. Consider whether a DDR bundle format should also be a Python installable (zipimport path) for agent tooling scenarios. Verdict: CANDIDATE.

§III.7  CLI Frameworks

Libraries for building the DDR App Framework's command-line interface — a first-class delivery surface.

 

[BRAIN-III-015] Typer  —  MIT

https://github.com/tiangolo/typer  |  pip: typer

Modern Python CLI framework built on Click, using Python type hints to auto-generate CLI arguments, options, and help text. Supports subcommands, autocompletion, and rich terminal output via Rich integration.

Relevance: The DDR App Framework CLI would expose all DDR Operations (INSERT, ACTIVATE, MODIFY, SUPERSEDE, DEPRECATE, VALIDATE, BUNDLE, UNBUNDLE_SCAN, UNBUNDLE_EXECUTE) as subcommands: ddr insert, ddr validate, ddr bundle, etc. Typer's type-hint-driven argument parsing maps cleanly to the strongly-typed Operation objects in BRAIN-II-003. Rich integration provides table-formatted validation findings output and progress bars for bulk operations.

DDR Tiers Touched: All operations (§7); CLI Presentation Layer

Notes: MIT license is commercially clean. Typer is maintained by the FastAPI author — well-maintained ecosystem. Consider coupling with Rich (BRAIN-III-016) for terminal output. Verdict: CANDIDATE.

 

[BRAIN-III-016] Rich  —  MIT

https://github.com/Textualize/rich  |  pip: rich

Python library for rich terminal output: syntax highlighting, tables, progress bars, panels, markdown rendering, and live-updating displays. Used by Typer, Pydantic, and many modern Python CLI tools.

Relevance: Rich is the display layer for the DDR App Framework CLI. Validation findings are naturally rendered as Rich tables (node ID, rule ID, severity, message). The VALIDATE operation summary (BLOCKER/ERROR/WARNING/INFO counts) renders as a Rich Panel. Graph metadata (node counts per tier, DIRTY propagation report) renders as a Rich tree. Rich also supports export to HTML for validation reports that can be saved alongside a project.

DDR Tiers Touched: CLI Presentation Layer — all user-facing output

Notes: MIT license. Zero transitive dependencies beyond pygments. Verdict: CANDIDATE. Pair with Typer (BRAIN-III-015) as the default CLI output layer.
